# الأمان والصلاحيات والنسخ الاحتياطي (Security, Permissions & Backup)

دليل تشغيلي متكامل لسياسات حماية البيانات، مصفوفة الصلاحيات والأدوار عبر Spatie Laravel Permission، قواعد سجل التدقيق والرقابة (Audit Log)، واستراتيجية النسخ الاحتياطي والاستعادة في حالات الطوارئ.

---

## 1. مصفوفة الأدوار والصلاحيات (Roles & Permissions Matrix)

يتم تأمين النظام باستخدام حزمة **Spatie Laravel Permission** وفق هيكل أدوار افتراضي واضح مع إمكانية التوسع:

```text
┌─────────────────────────────────────────────────────────────┐
│                    Role-Based Access Control                │
├──────────────────────────────┬──────────────────────────────┤
│ 1. Admin Role (المدير العام)  │ 2. User / Cashier (الموظف)   │
│    - صلاحيات كاملة           │    - إصدار فواتير وسندات     │
│    - تقارير أرباح وتكاليف    │    - بحث وإضافة عملاء        │
│    - إلغاء وإدارة صلاحيات    │    - ممنوع من الأرباح والتعديل│
└──────────────────────────────┴──────────────────────────────┘
```

## 2. قواعد وهيكلة سجل الرقابة والتدقيق (Audit Log Guidelines)

سجل التدقيق هو الحصن الرقابي للنظام لحماية أموال وبضائع المتجر ومنع التلاعب، وتخضع سجلاته للقواعد التالية:

1. **طبيعة السجلات غير القابلة للتعديل أو الحذف (Immutable Log Records):**
   * جدول `audit_logs` محمي برمجيًا من أي عمليات `UPDATE` أو `DELETE`، ولا يتم حذف أي حركة منه نهائيًا.
2. **العمليات التي يتم تسجيلها إلزاميًا (Audited Events):**
   * اعتماد فاتورة بيع جديدة أو تعديل مسودة.
   * إلغاء فاتورة بيع معتمدة (مع توثيق سبب الإلغاء ورصيد العميل المتأثر).
   * إنشاء مستند مرتجع مبيعات وتفاصيل الكميات المرتجعة.
   * اعتماد فاتورة شراء وتوريد بضاعة جديدة للمخزن.
   * تسجيل سند قبض مالي أو تعديل دفعة.
   * إجراء تسوية مخزنية يدوية (Stock Adjustment / Deposit).
   * تعديل أسعار التكلفة أو أسعار البيع لأي صنف.
   * تغيير أو منح صلاحيات وأدوار للمستخدمين.
3. **البيانات المسجلة مع كل حدث:**
   * معرف المستخدم (`user_id`)، نوع العملية (`action_type`)، الموديل المستهدف (`auditable_type` & `id`).
   * البيانات السابقة (`old_values`) والبيانات اللاحقة (`new_values`) بتنسيق JSON.
   * عنوان الجهاز (`ip_address`) وبيانات المتصفح والتاريخ والوقت بالثانية.

## 3. سياسة النسخ الاحتياطي واستعادة البيانات (Backup & Disaster Recovery Policy)

لحماية النشاط التجاري من مخاطر تعطل الأجهزة أو التلف الطارئ لقاعدة البيانات:

### 3.1 جدول وتكرار النسخ الاحتياطي (Backup Frequency)
* **النسخ اليومي التلقائي (Automated Daily Backup):**
  * يتم تشغيل مهمة مجدولة (Cron Job) في نهاية كل يوم عمل (الساعة 12:00 منتصف الليل) لتصدير نسخة كاملة ومضغوطة من قاعدة البيانات بصيغة `.sql.gz`.
* **النسخ اليدوي الفوري (On-Demand Backup):**
  * زر مخصص في لوحة المدير لإنشاء نسخة احتياطية فورية وتنزيلها بضغطة زر واحدة قبل إجراء أي تسويات جردية ضخمة أو صيانة للنظام.
* **الاحتفاظ بالنسخ (Retention Policy):**
  * الاحتفاظ بآخر 30 نسخة يومية، وآخر 12 نسخة شهرية، مع الحذف التلقائي لما زاد عن ذلك لتوفير المساحة.

### 3.2 التخزين خارج السيرفر (Offsite Cloud Storage)
* في بيئة الإنتاج الفعلي (Production)، تُرسل النسخة الاحتياطية تلقائيًا إلى مساحة تخزين سحابية منفصلة وآمنة (مثل AWS S3, Wasabi, أو خادم تخزين خارجي) مع تشفير الملفات.

### 3.3 اختبارات الاستعادة في حالات الطوارئ (Restore Drills)
* يتم توثيق أمر استعادة سريع ينفذه مسؤول النظام عبر سطر الأوامر:
```bash
# أمر فك الضغط والاستعادة السريعة لقاعدة البيانات
gunzip < /path/to/backup/sroor_backup_2026-08-08.sql.gz | mysql -u root -p sroor_db
```
* يُجرى اختبار تجريبي دوري كل 3 أشهر على خادم اختبار للتأكد من سلامة ملفات النسخ وصلاحيتها للعمل الفوري دون أخطاء.
