# Localization (ar/en) — Score 3/10

> Branch `feature/multi-tenant` · 2026-10-07 · read-only multi-agent analysis · secrets redacted

## Executive summary

After deduplicating the sub-agent findings, 7 distinct issues remain: 1 critical and 6 medium.

The translation pipeline itself is in good shape. lang/*.php is the single source of truth, `lang:export` runs automatically before every build, the generated bundle is in sync, ar and en keys match in 24 of 25 files, placeholders are consistent, and the frontend uses translation helpers cleanly. Two problems still outweigh that.

1. **Critical security hole (3 sub-agents confirmed it on their own).** The public, no-login endpoint GET /api/v1/system/translations passes the `locale` query value or `X-Locale` header straight into `lang_path()`, `glob()` and `trans()` without checking it (backend/app/Actions/System/GetTranslationsAction.php:18-22,40; backend/app/Http/Controllers/Api/SystemContextApiController.php:47; backend/routes/api.php:30). A request with `?locale=../config` makes the server load and return every config/*.php array as JSON. That includes APP_KEY and the DB, mail and Telegram credentials whenever the config cache is not active, and several deploy scripts clear that cache. It also makes the server run any existing *.php file in a folder reachable by `../`. One local run listed key names only and confirmed that `app.key` came back non-empty. This must be handled as an incident, not as localization cleanup.

2. **English cannot be used in practice.** Nothing on the server ever calls `setLocale()`, so every `__()` message (toasts, 422 validation errors, auth errors, print views) comes out in Arabic. On the frontend there is no language switcher, and the guest boot (App.vue:118, stores/appConfig.js:84,90) and LoginView.vue:419 overwrite any saved 'en' with 'ar'.

On top of that:
- **About 80 translation keys are used in code but missing from both ar and en.** Users see raw keys in toasts, export column headers, printed A4 journals and the super-admin tenant forms.
- **79 `__('key') ?: 'Arabic literal'` fallbacks can never run**, because a missing key returns the key string itself. They hide the missing keys and drop values such as the invoice number.
- **Error messages in the core stock, invoice and treasury services are hardcoded Arabic.**
- **Whether a unit allows only whole quantities depends on matching free-text Arabic unit names** (InvoiceService.php:65).

Score: 3/10. The translation infrastructure is sound and the fixes are mostly mechanical. The score is held down by one critical unauthenticated secret-disclosure and file-inclusion bug, and by a bilingual promise that cannot currently be met.

### 1. [CRITICAL] Unauthenticated path traversal in the locale param of /api/v1/system/translations returns every config/*.php array, including APP_KEY
- **Location:** `D:\projects\sroor\backend\app\Actions\System\GetTranslationsAction.php:18`
- **Effort:** S
- **Evidence:** SystemContextApiController.php:47 takes `$locale = (string)($request->query('locale') ?: $request->header('X-Locale') ?: app()->getLocale())` and never validates it. GetTranslationsAction:18-22 runs `glob(lang_path($locale).'/*.php')` and then `trans($group, [], $locale)`. Translator::get() skips the '/' and '\\' check that only setLocale() does (Translator.php:576-580), and FileLoader::loadPaths requires "{$path}/{$locale}/{$group}.php" (FileLoader.php:128). The route sits outside ApiTokenAuth (routes/api.php:30), so no login is needed. I ran a local proof that printed key names only: execute('../config') returned the groups app,auth,cache,database,filesystems,logging,mail,permission,pulse,queue,services,session,telescope,tenancy. app.key was present and non-empty, and database.connections.mysql exposed host/username/password fields. Step 3 (line 40) also reads any '<locale>.json' file, e.g. '../composer'. The same unvalidated X-Locale header goes into the same action from GetSystemContextAction.php:103 (authenticated).
- **Impact:** Anyone on the internet can call GET /api/v1/system/translations?locale=../config (or send X-Locale: ../config) and get back the app's resolved config arrays: APP_KEY (lets them forge or decrypt encrypted cookies and payloads), DB/mail/Redis credentials, third-party service tokens (Telegram etc. in config/services.php) and tenancy settings. How much leaks in production depends on whether config is cached. Without config:cache, env() resolves and the real secrets are returned. With config:cache, env() inside a raw require may return null, but literal defaults still leak. Any other directory holding *.php files that return arrays, or side-effecting PHP files, can also be include()'d.
- **Recommendation:** Treat this as an incident. Whitelist the locale right away (`in_array($locale, config('app.supported_locales', ['ar','en']), true)`, otherwise use the default) in both the controller and GetSystemContextAction, or validate it in a FormRequest (`Rule::in(['ar','en'])`). Rotate APP_KEY and any credentials reachable through config/ on production, and check web server logs for `locale=..` or X-Locale traversal attempts. Add a regression test asserting that `?locale=../config` returns ar/en data only and never an 'app' or 'database' group.
- **Verification:** I confirmed this from the code, and I found no guard anywhere in the path.

1. **No login needed.** routes/api.php:30 registers GET /v1/system/translations before the ApiTokenAuth group (line 33). Its only middleware is ResolveApiTenancy. That middleware just initializes a tenant when it finds one, and when no X-Tenant header is sent it lets the request through, so it does not block anything.

2. **The locale is never checked.** SystemContextApiController.php:47 takes `locale` from the query string or the X-Locale header and passes it straight to GetTranslationsAction::execute. There is no FormRequest, no allow-list of locales, and no middleware in bootstrap/app.php that cleans it.

3. **The path climbs out of lang/.** GetTranslationsAction.php:18-22 runs lang_path($locale), so '../config' points at backend/config. is_dir() is true for that folder, and glob('*.php') returns every config file (app, auth, cache, database, mail, services, session, tenancy and the rest are present). It then calls trans($group, [], $locale) for each file.

4. **The framework does not stop it.** I checked vendor Laravel v13.25.0:
   - Translator::get() (line 151) never validates the locale. Only setLocale() rejects '/' and '\' (lines 576-580).
   - getLine() calls Arr::get($loaded, null), which returns the whole array. trans('app') therefore returns the entire config array, after array_walk_recursive replacement.
   - FileLoader::loadPaths (lines 124-131) builds "{$path}/{$locale}/{$group}.php" and loads it with getRequire, so lang/../config/app.php is executed and its return value comes back.

5. **What leaks.** config/app.php:100 is 'key' => env('APP_KEY'). config/services.php holds the Telegram bot token, AWS key and secret, Postmark, Resend and Slack tokens, all read through env(). database.php and mail.php hold the database and mail credentials.

6. **A second, smaller leak.** Step 3 (lines 40-43) reads any lang/<locale>.json. A locale such as '../composer' exposes composer.json, which is minor.

7. **The authenticated path behaves the same.** It goes through GetSystemContextAction, as the finding says.

The only thing that lowers the impact: if production runs config:cache, env() inside the raw require may return null and only the literal defaults would leak. That depends on the deployment and cannot be seen in the code. Without a config cache this is a full secret leak (APP_KEY, database password, bot tokens) to anyone on the internet, so critical stands.

1. There is no locale switcher anywhere in resources/js. Nothing changes `appConfigStore.locale` at runtime except the two fetch actions. Both guest calls force Arabic: `fetchTranslations()` defaults to 'ar', and LoginView passes 'ar' explicitly. That call also writes `app_locale='ar'` to localStorage.
